# ADR 0018 — Release approval is a human with a password

## Status

Accepted.

## Context

A release is the one act this product must never do on the word of a machine. A
machine can build it, test it, and propose it; a person must decide to ship it.
The question this ADR answers is: where does that decision live, and what proves
it was made?

Two earlier drafts got this wrong, and the reasons are more useful than either
answer.

### Draft one left the key on the machine being gated

The first draft kept a release key usable on the bridge machine and let a
Telegram `/release approve` trigger it. That is not a gate. The `phone` identity
signs on whichever machine runs the bridge, so an approval signed as `phone`
proves the bridge machine acted, not that the operator did. A gate whose key
lives on the machine being gated is not a gate.

### Draft two fixed the cryptography and broke the product

The second draft had the operator run `ferry` on a phone to sign the approval.
Correct, and unusable. Ferryman is for people who are not technical, and a design
that assumes a terminal emulator on a phone has quietly changed who the product
is for. Correct and unusable is not correct. If any part of a release flow needs
a non-technical person to touch a command line, it is wrong.

## Decision

The primitive already exists and nobody noticed it solved this. An operator's
signing key derives from the machine seed and is **sealed at rest with their
password** — PBKDF2-SHA256, 600k iterations, XChaCha20-Poly1305 — in
`crates/ferryman-server/src/operators.rs`. The dashboard does not hold that key
until the person signs in.

So: **the fleet cannot sign as the operator, because the fleet does not have the
password.** Signing in IS the gate. No new key, no second device, no new secret
to lose.

### The flow

1. A machine writes a signed **release request** in the channel: version, exact
   commit, CI conclusion, changelog summary. One writer per path, like every
   record here (`release/request.<id>.json`).
2. Telegram says a release is waiting and links to it. That is ALL Telegram
   does. It holds no authority and must not be able to cause a signature on its
   own.
3. A release page in the dashboard shows what is being approved — version,
   commit, CI, changelog — and an approve/deny. It shows the reasoning, not a
   bare yes/no: a gate offering two buttons and no information is a rubber stamp
   with extra steps. It must read well on a phone; the operator will be standing
   somewhere else.
4. Approving signs an **approval decision** with the operator key already
   unsealed in the session (`release/decision.<id>.<operator>.json`). The signing
   machine verifies it against the roster, then tags, signs and pushes.
5. The tag is signed with a **release key** separate from the operator's
   personal GPG identity. Its public half is published in the repo and in
   `docs/RELEASE_PROCESS.md`.

## What must refuse

The gate refuses, loudly and with a reason, an approval that:

- does not verify, or names an operator the roster does not know;
- approves a version or **commit** different from the request — approving this
  release must never authorise a different one; this is the attack the design
  turns on, and it is tested explicitly;
- is older than a short horizon (24 hours);
- carries a CI conclusion that is not green. The gate is for judgement, not for
  overriding the machine.

## The release key

The release key is a separate Ed25519 keypair, generated by `ferry release key`,
stored owner-only in the attachment (`keys/release.key`), and never in the
channel. Its public half is published in the repository. It is deliberately not
the operator's personal GPG identity: even sealed, a personal key on a box
running autonomous agents puts every commit that key has ever meant behind the
weakest process on that machine.

## Reaching it from afar

The dashboard binds to loopback and that stays the default. Getting to it from
outside is a transport problem, not a trust one: a tunnel the operator already
runs puts the same loopback page on their phone without weakening anything,
because the page still demands a password. This ADR does not invent an auth
bypass for remote access, does not add a token in a URL, and does not widen the
Host guard by default.

## Constraints

- No secret traverses Telegram, and nothing logs, echoes or persists a password
  or private key. The password unseals a key in memory for a session and is
  never stored.
- One writer per path; signed records; verified against the roster. No state that
  exists only in the dashboard or only in the bridge.
- Channel content rendered into the page is untrusted text written by other
  machines, and is escaped.
- No heavyweight new dependencies.
