# ADR 0018 — Releases approved from Telegram, signed on a machine

## Status

Accepted.

## Context

The owner asked: *"I would like to be able to automate, from afar, with no need
to sign locally. Could we do a request via telegram?"*

A release is the one act this product must never do on the word of a machine. A
machine can build it, test it, and propose it; a person must decide to ship it.
The question this ADR answers is: where does that decision live, what carries
it, and what proves it was made.

Two earlier drafts got this wrong, and the reasons are more useful than either
answer.

### Draft one left the personal key on the machine being gated

The first draft kept a signing key usable on the bridge machine and let a
Telegram `/release approve` trigger it. That is not a gate: an approval signed
by a key that lives on the machine being gated proves the bridge machine acted,
not that the operator did. And because the key was the operator's *personal*
GPG identity, sitting passphrase-less on a box that runs autonomous agents, it
put every commit that identity had ever meant behind the weakest process on the
box.

### Draft two fixed the cryptography and broke the product

The second draft had the operator run `ferry` on a phone to sign the approval.
Correct, and unusable. Ferryman is for people who are not technical, and a
design that assumes a terminal emulator on a phone has quietly changed who the
product is for. If any part of a release flow needs a non-technical person to
touch a command line, it is wrong.

## Decision

The obvious version is forbidden for a reason that stands: **the passphrase must
never travel over Telegram.** The bridge's own help text says "Do not send
credentials here", and a release approval is the most dangerous place that rule
could be bent. So the passphrase does not move; the *authorisation* moves.
Telegram carries a decision, never a secret.

Draft one's real error was not the Telegram message — it was the key. The fix is
not to abandon Telegram, it is to give the machine a key that forfeits
**releases and nothing else**.

### The flow

1. A machine writes a signed **release request** in the channel: version, exact
   commit, CI conclusion, changelog summary, and who prepared it. One writer per
   path, like every record here (`release/request.<id>.json`).
2. The bridge puts it on Telegram, showing *what* is being approved — version,
   commit, CI, changelog — rather than asking a bare yes/no. A gate that offers
   two buttons and no information is a rubber stamp with extra steps.
3. The approver types `/release approve <version>` or
   `/release deny <version> <why>` — structured commands in
   `crates/ferryman-cli/src/telegram.rs`, beside `/order` and `/to`. Structured
   only: ADR 0008's rule is that free text must never be silently promoted to a
   signed action. Authorization is the existing `from.id == approver_id` and
   nothing new. The bridge writes a signed **decision** record
   (`release/decision.<id>.<bridge>.json`) recording the approver's name and
   Telegram id, then verifies, tags, signs and pushes.
4. The tag is signed with a **release key**, separate from the operator's
   personal GPG identity. Its tag message records that the release was approved
   remotely and by whom, because someone reading `git tag -v` a year from now
   should be able to tell which arrangement produced it.

## What the signature now attests to

A Ferryman release signature no longer means "a human typed a passphrase at the
machine". It means **"the approver said yes from their phone, and the bridge
machine witnessed it"**. The decision record carries the approver's Telegram
`from.id` inside the signed payload, so the claim cannot be rewritten after the
fact — but the cryptographic proof that the *machine* wrote the decision is the
bridge's, not the operator's. The operator's personal identity is never behind
this path. This is the trade that makes remote approval acceptable, and it is
stated in `docs/RELEASE_PROCESS.md` rather than left to be discovered.

## What must refuse

The gate refuses, loudly and with a reason, an approval that:

- does not verify, or was not written by the bridge machine the roster knows;
- approves a version or **commit** different from the request — approving this
  release must never authorise a different one; this is the attack the design
  turns on, and it is tested explicitly;
- is older than a short horizon (24 hours) — an approval sitting unread
  overnight is not consent to ship whatever main became;
- carries a CI conclusion that is not green. The gate is for judgement, not for
  overriding the machine.

## The release key

The release key is a separate, passphrase-less GPG key generated by
`ferry release key`. Its private half stays in the signing machine's GPG keyring
and never enters the channel; its public half is exported to `keys/release.asc`
and published in `docs/RELEASE_PROCESS.md` exactly as the current personal key
is, with its fingerprint. It is deliberately **not** the operator's personal GPG
identity: even sealed, a personal key on a box running autonomous agents puts
the whole identity behind the weakest process on that box. A release key
forfeits releases and nothing else.

## Constraints

- No secret traverses Telegram, and nothing logs, echoes or stores a passphrase
  or private key. The passphrase never leaves the operator's head.
- One writer per path; signed records; verified against the roster. No state
  that exists only in the bridge.
- The existing approver check is not weakened: `from.id == approver_id`, for
  text and commands alike.
- No heavyweight new dependencies. Toolchain pinned 1.97, edition 2024.
